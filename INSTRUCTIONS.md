## 1. Проект за 30 секунд

* **«Распознаватель»** — портативная офлайн-программа для **Windows 10/11 x64**:
  OCR текстов с экрана и изображений (Tesseract, 15 языков), QR/штрих-коды
  (zxing-cpp + pyzbar), скриншоты области экрана, офлайн-перевод EN↔RU
  (ctranslate2 + sentencepiece, модели Argos), история распознаваний, трей,
  автозапуск, настраиваемые горячие клавиши.
* **Интерфейс:** HTML/CSS/JS внутри нативного окна **pywebview** (WebView2 через
  pythonnet). Мост «JS ↔ Python» — `api.py` (класс `Api`, методы вызываются из JS).
* **Сборка:** PyInstaller → портативная папка `dist/Raspoznavatel/`
  (`build.spec`, onedir, `console=False`), установщик — NSIS (`installer.nsi`).
  Официальные релизы собраны **в Linux через Wine** — и ты можешь так же.
* **Ключевые модули:** `main.py` (точка входа, selftest), `api.py`, `ocr.py`,
  `qr_reader.py`, `translator.py`, `screen_capture.py`, `tray.py` (трей, ctypes),
  `proc.py` (запуск процессов БЕЗ консоли), `config.py` (пути, настройки,
  `APP_VERSION`), `log.py`.
* **Версия живёт в ДВУХ местах** (синхронизируй обязательно):
  `config.py:APP_VERSION` и `installer.nsi` (OutFile, VIProductVersion,
  FileDescription, FileVersion, ProductVersion, DisplayName, DisplayVersion).
  В `README.md`, в интерфейсе и в комментариях номер версии НЕ пишется —
  иначе на сайте вечно видна старая версия (урок L50). Интерфейс берёт версию
  из `get_info()`, а готовые файлы — со страницы Releases.
* **Ресурсы:** `resources/tessdata` (15 языков, в git), `resources/tesseract`
  (движок, в git), `ui/assets/fonts` (в git), `resources/argos/*.argosmodel`
  (модели перевода, **в git НЕ входят** — качаются, лежат в `.gitignore`).

1. Прочитай этот файл и `README.md`; посмотри `git log --oneline | head` —

   после «умершей» сессии — начни с `UNIVERSAL-RESUME.md` в корне (порядок

2. Проверь бэкап-систему: `bash tools/gh-backup.sh status`. Нет токена → проси
   у владельца ОДИН раз, положи по §7. Не продолжай без токена.
3. Склонируй проект (или убедись, что он есть и на `main`, `git pull`).
4. Прогони быстрые тесты БЕЗ сборки: `python3 tests/test_logic.py`
   (должно быть «0 провалено»; если падают ДО твоих правок — скажи владельцу и

### 4.3 Сборка exe (Wine)

**Полная пересборка релиза одной командой (рекомендуется):**
```bash
bash tools/build_release_wine.sh all        # doctor -> env -> build -> check -> package
# по этапам: doctor | env | build | check | package | verify | clean
# готовые ассеты: <workspace>/release_assets/ (Setup.exe + portable.zip)
```
Скрипт сам ставит проверки (диск ≥5 ГБ, ресурсы, тесты), сам собирает, гоняет
selftest и ОБЯЗАТЕЛЬНО убирает wine-процессы после каждого шага (урок L33).
Ниже — те же шаги вручную, если нужно отладить отдельный этап.

```bash
export WINEDEBUG=-all WINEPREFIX=<workspace>/wineprefix
cd <workspace>/raspoznavatel
rm -rf build dist
xvfb-run -a wine64 "C:\\winpy\\python.exe" -m PyInstaller build.spec \
    --noconfirm --clean 2>&1 | tee /tmp/pyi.log | tail -5   # НЕ редирект в файл (L11)
ls dist/Raspoznavatel/Raspoznavatel.exe
```
Сборка занимает ~3 минуты. Предупреждения «Scripts not on PATH» от pip и
«OpenBLAS WARNING» при запуске — безвредны.

### 4.4 Проверка собранного (обязательно)

**После проверки ОБЯЗАТЕЛЬНО удали рабочие данные из папки сборки** (урок L35):

### 4.5 Установщик и портативный zip
Перед упаковкой убедись, что в `dist/Raspoznavatel` ТОЛЬКО `App` и
`Raspoznavatel.exe` (урок L35) — иначе в установщик попадёт ~200 МБ рабочих
данных selftest.
```bash
makensis -V2 installer.nsi          # → dist/Raspoznavatel-<ВЕРСИЯ>-Setup.exe (~455 МБ, ~7 мин)
# ТРЕБОВАНИЕ ВЛАДЕЛЬЦА (2026-10-18): в КОРНЕ zip лежат Raspoznavatel.exe и App/,
# БЕЗ вложенных dist/Raspoznavatel/ — архивируем СОДЕРЖИМОЕ папки:
cd dist/Raspoznavatel
7z a -tzip -mx=1 "$WS/Raspoznavatel_v<ВЕРСИЯ>_win64_portable.zip" "*"
```
Проверь структуру до публикации: `7z l …zip | head` — первые записи
`Raspoznavatel.exe`, `App/…`. Иначе владелец получит лишних два уровня папок.
Тихую установку NSIS в Wine НЕ проверяй — не работает ни один NSIS (L14).
Целостность установщика подтверждай так: `7z l dist/*-Setup.exe | tail`

### 4.7 Релиз на GitHub (правило «ОДИН чистый релиз»)
Владелец требует: на странице Releases всегда **один** релиз — актуальная
версия, описание = «что за программа, для чего, как поставить», БЕЗ «что нового»
и истории. Порядок через API (python3 urllib, токен в заголовке):
1. `GET /repos/{o}/{r}/releases` → `DELETE` все релизы кроме целевого тега
   (ассеты удалятся вместе с релизом);
2. `DELETE /repos/{o}/{r}/git/refs/tags/<старые теги>`;
3. запушь новый тег `v<ВЕРСИЯ>` (`git tag -a … && git push origin v<ВЕРСИЯ>`);
4. `POST /releases` (`tag_name`, `name`, `body` — чистое описание);
5. загрузи оба артефакта на `upload_url` релиза (стриминг: `urlopen(req, fileobj)`,
   `Content-Type: application/octet-stream`, L25);
6. **сожми историю**: `bash tools/build_release_wine.sh squash` (L52) — на
   главной странице не должно остаться ни одного упоминания старых версий;
7. при необходимости `PATCH /repos/{o}/{r}` — описание репозитория и видимость
   (в теле ОБЯЗАТЕЛЬНО `name`, L24).

## 6. Правила репозитория, релизов и описаний

* Репозиторий **публичный**; описание (About) — одна строка: что за программа
  и главные возможности. Без «auto-backup» и технического мусора.
* Releases: один релиз = одна актуальная версия = установщик + портативный zip;
  тело релиза — описание программы и установка, НЕ changelog.
* `README.md` — описание программы и способов сборки; журналы «что было
  в старых версиях» не вести. История правок — в ветках `archive/*` и в уроках
  раздела 8; на главной странице репозитория и в сообщениях коммитов
  упоминается ТОЛЬКО текущая версия (L50, L52).
* Ветки `savepoint-*` и `pre-rollback-*` — точки отката бэкап-системы:
  не удаляй их молча (чистятся скриптом сами, держится 10 последних).
* Большие бинарники (модели, dist) в git НЕ коммитятся — только ассетами релиза.
* Тег релиза создаётся при публикации и ВСЕГДА стоит на единственном коммите
  `main` (текущая версия); после каждого релиза история main сжимается в один
  коммит этапом `squash`, а тег обновляется force-пушем (L52). Старые релизы и
  теги удаляются (правило «ОДИН чистый релиз»).

## 8. Уроки (Lessons Learned)

Формат: **если X → делай Y, иначе получишь Z.** Новые уроки дописывай в конец
своего подраздела (§9); старые не удаляй.

### Песочница, пути, git
* **L1.** Если скрипту (python/heredoc) нужен путь workspace → передавай его
  через `sys.argv`/переменную окружения (`$ARENA_WORKSPACE`), а не литералом
  `/home/user` в тексте → иначе песочница перепишет литерал в строку
  `"$ARENA_WORKSPACE"`, и скрипт упадёт с FileNotFoundError.
* **L2.** Не полагайся на `~` и `$HOME`: в песочнице это `/tmp`, он не переживает
  сессию → иначе потеряешь файлы (токен, конфиги) между сессиями.
* **L3.** Нет токена → проси у владельца один раз (scope `repo`) и клади в
  `.git-credentials` → иначе «No such device or address» при clone/push.
* **L4.** Собираешься править проект → сначала `gh-backup.sh snapshot` →
  иначе при поломке некуда откатиться.
* **L5.** `curl` в песочнице обычно нет → GitHub API и скачивания делай
  через `python3 urllib` → иначе «command not found» и потерянное время.

### Windows-код (ctypes, трей, процессы)
* **L6.** Пишешь Win32-колбэк на ctypes → `WPARAM/LPARAM/LRESULT` только
  `c_size_t/c_ssize_t` и явные `argtypes/restype` у ВСЕХ вызовов → иначе на x64
  указатели обрежутся до 32 бит: обработчики получат мусор (так родилось
  «белое меню с невидимыми надписями» в одной из старых сборок).
* **L7.** Рисуешь пункты меню сам (`MF_OWNERDRAW`) → держи фолбэк на системное
  меню `MF_STRING` (флаг `_ownerdraw_failed` + try/except вокруг отрисовки) →
  иначе любой сбой отрисовки = пустое белое меню у пользователя.
* **L8.** Запускаешь внешний процесс из программы → только `proc.run/proc.kwargs`
  (`CREATE_NO_WINDOW` + `STARTUPINFO` c `SW_HIDE`) → иначе у пользователя на
  мгновение мелькает чёрное окно командной строки.
* **L9.** Сторонняя библиотека сама дёргает subprocess (pytesseract→tesseract.exe)
  → прокинь флаги через `proc.patch_module(внутренний_модуль)` → иначе мигание
  консоли останется, хотя «свой» код чист.
* **L37.** Настраиваешь Win32-прототипы пачкой в одной функции → оборачивай
  КАЖДУЮ привязку в try/except и проверяй, в какой DLL живёт функция
  (`FillRect` — в user32, НЕ в gdi32) → иначе одна опечатка роняет всю
  настройку, поток трея умирает сразу после старта, а значок «дорисовывает»
  watchdog в своём потоке: иконка видна, но не реагирует ни на левый, ни на
  правый клик, а повторный запуск exe молча завершается (так одна из сборок уехала
  к владельцу с нерабочим треем — 2026-10-18).
* **L38.** Создаёшь окно трея и значок → ТОЛЬКО в том потоке, который качает их
  сообщения; watchdog'у запрещено создавать окна (он перезапускает поток
  целиком), а здоровье трея меряй ПУЛЬСОМ насоса (`SetTimer`+`WM_TIMER` раз в
  секунду → `_last_beat`), а не флагом `icon_shown` → иначе получаешь
  «значок-муляж»: виден, но мёртв.
* **L39.** Показываешь/прячешь окно из потока трея → НЕ вызывай pywebview
  `window.show()/hide()`: это синхронный `Invoke` в GUI-поток WinForms, и если
  тот занят — поток трея встаёт намертво (иконка «залипает» после первого
  клика). Работай Win32 `ShowWindow/SetForegroundWindow`
  (`api.win_force_show/win_force_hide`), а колбэки уводи в отдельный поток
  (`TrayIcon._spawn`) → иначе клик по иконке глушит весь трей.
* **L40.** Делаешь single-instance → второй экземпляр обязан ДОЖДАТЬСЯ
  подтверждения первого (именованное событие `CreateEventW` +
  `WaitForSingleObject` ~2 с) и при отсутствии ответа ЗАПУСТИТЬСЯ САМ
  (перехват) → иначе «программа не запускается вообще»: первый экземпляр висит,
  второй молча выходит, а пользователь видит только мёртвую иконку.
* **L41.** Перезапускаешь поток трея → вводи «поколение» (generation) и привяжи
  к нему цикл сообщений и уборку значка → иначе залипший старый поток,
  проснувшись, снесёт НОВЫЙ значок и пользователь снова останется без трея.

### Сборка в Wine
* **L10.** Ставишь `wine64` без мета-пакета `wine` → создай симлинки
  `/usr/bin/wine64 → ../lib/wine/wine64` и `wineserver`, и поставь `xauth` →
  иначе «command not found» и «xvfb-run: xauth not found».
* **L11.** Запускаешь Windows-Python в Wine → НЕ оборачивай в `cmd /c` и НЕ
  редиректь вывод в файл (`> log`) → иначе `Fatal Python error: init_sys_streams`
  / `OSError WinError 6`; запускай `wine64 python.exe …` напрямую, вывод через
  pipe (`| tee log`).
* **L12.** Нужен Windows-Python с tkinter → бери python-build-standalone
  (install_only tar.gz) → иначе: в NuGet-пакете нет tkinter, а официальный
  MSI-бандл 7z распаковывает частично — часы возни впустую.
* **L13.** Проверяешь зависимости в Wine → НЕ импортируй `clr`/pythonnet
  (Wine-mscoree падает с assert); анализ PyInstaller модули не исполняет, сборке
  не мешает. И помни: пакет `pywebview` импортируется как `webview` →
  иначе ложный ModuleNotFoundError.
* **L14.** Хочешь проверить NSIS-установщик тихой установкой в Wine → не трать
  время: там не запускается НИ ОДИН NSIS-установщик (проверено мини-примером);
  проверяй `7z l` (число файлов/объём) + selftest портативной сборки.
* **L15.** Ищешь отчёт selftest → он в `Raspoznavatel_data/selftest_report.txt`
  рядом с exe, не в stdout → иначе решишь, что проверка «ничего не вывела».
* **L16.** Передаёшь пути в Wine → собирай строку `Z:\…` из ФАКТИЧЕСКОГО пути
  workspace (env), а вывод Wine грепь с `grep -a` (в нём UTF-16 с нулями) →
  иначе «file not found» и «binary file matches».
* **L17.** Свободного места < 5 ГБ → снеси `wineprefix`, `dist_console`,
  `build_src` ДО новой сборки → иначе сборка умрёт посередине на полном диске.
* **L33.** Wine-шаг завершился (wineboot, pip, PyInstaller, selftest) → убери
  дерево Wine ШТАТНО и дождись его: `wineserver -k` и СРАЗУ `wineserver -w`
  (ждать выхода!), и только потом точечно `pkill -x Xvfb`, если он жив; весь
  скрипт сборки запускай под субрепером `tini -s -- bash …` (пакет `tini`,
  плюс `procps` ради `ps`/`pgrep`) → иначе PID 1 песочницы (node) чужих сирот
  не подбирает, зомби от wine-процессов копятся сотнями, песочница исчерпывает
  лимит процессов, и сборка умирает на ровном месте (потерянная сессия
  2026-10-18). Агрессивный `pkill -f wine64` — худший вариант: он плодит
  сирот и сам остаётся зомби. Готовый скрипт: `tools/build_release_wine.sh`
  (этапы doctor/env/build/check/package/verify/all/clean) — уборка встроена
  после каждого wine-вызова и в `trap EXIT`.
* **L34.** Хочешь selftest собранного exe → гоняй `RASPOZ_SELFTEST=1` на САМОМ
  `dist/Raspoznavatel/Raspoznavatel.exe` и читай отчёт из файла рядом с ним
  (L15); консольную копию (`console=True`) не строй: в Wine 8.0 она не
  загружается (`wine: failed to open … c0000135`), а stdout всё равно не нужен
  → иначе минус 4 минуты и 800 МБ диска на каждом прогоне.
* **L35.** Прогнал selftest → СРАЗУ снеси `dist/Raspoznavatel/Raspoznavatel_data`
  и `dist/Raspoznavatel/Screenshots` (там распакованная модель перевода ~200 МБ,
  логи, tmp) и проверь, что в папке остались только `App` и `Raspoznavatel.exe`
  → иначе эти гигабайты уедут в установщик и в портативный zip к пользователю.
* **L36.** Проверяешь архив листингом (`7z l … | grep -q …`) в скрипте с
  `set -o pipefail` → сначала прочитай листинг ЦЕЛИКОМ в переменную, потом
  грепь её (`grep -q` обрывает `7z` сигналом SIGPIPE, и с pipefail проверка
  «падает» на полностью исправном архиве) → иначе ложный провал на последнем
  шаге, когда всё уже собрано.
* **L42.** Гоняешь Wine вручную (вне `tools/build_release_wine.sh`) → оборачивай
  запуск в субрепер: `tini -s -- xvfb-run -a wine64 …`, а после —
  `wineserver -k; wineserver -w` → иначе каждый запуск оставляет 10-30 ВЕЧНЫХ
  зомби (PID 1 песочницы — node, чужих сирот не подбирает), и к концу сессии
  таблица процессов забита.
* **L43.** Проверяешь трей/оконный код → юнит-тестов на Linux НЕДОСТАТОЧНО:
  гоняй `tests/tray_win_smoke.py` в Wine (этап `smoke` в скрипте сборки) — он
  проверяет настоящий Win32: насос сообщений, клики по значку, зависший колбэк,
  перезапуск watchdog'ом, подтверждение второму экземпляру → иначе «158/158
  зелёных» спокойно пропускают владельцу мёртвую иконку.

* **L44.** Передаёшь путь в Wine → бери ФИЗИЧЕСКИЙ путь (`pwd -P`,
  `os.path.abspath`), а не тот, что показывает `$PWD`: рабочая папка песочницы
  смонтирована так, что `Z:\home\user\…` из Wine НЕ виден
  (`os.path.exists` → False), и `python.exe` с таким путём молча виснет без
  единой строчки вывода → иначе час ищешь «зависший тест», которого нет.
* **L45.** Перезапускаешь поток трея → регистрируй для каждого поколения СВОЁ
  имя класса окна (`tray_class_name(generation)`) и ищи окно по ЗАГОЛОВКУ
  (`find_tray_hwnd()`), а не по классу → иначе, пока старый (залипший) поток
  жив, `CreateWindowExW` того же класса в новом потоке отказывает (проверено в
  Wine) и значок не возвращается: пользователь снова без трея.
* **L46.** Дымовой тест в Wine → завершай его `os._exit(rc)` и печатай прогресс
  с `flush=True` (как `main.py` после закрытия окна) → иначе Wine не может
  остановить процесс с висящими daemon-потоками, тест «зависает» на выходе,
  `timeout` убивает его БЕЗ отчёта, и ты не понимаешь, что именно сломалось.
* **L47.** Watchdog чего-либо перезапускает → дай новому потоку льготное время
  (`STARTUP_GRACE`) и выдержи паузу между перезапусками (`RESTART_COOLDOWN`) →
  иначе watchdog устраивает шквал перезапусков, каждый из которых обрывает
  предыдущую попытку, и подсистема не поднимается НИКОГДА.
* **L48.** Правил код, который выполняется ТОЛЬКО в Windows (ctypes-ветки под
  `if os.name == "nt"`) → прогони статическую проверку имён
  (`python3 -m pyflakes *.py`, встроена в этап `doctor` скрипта сборки) и держи
  `from ctypes import wintypes` ВНУТРИ самой функции → иначе NameError не
  ловится ни тестами на Linux, ни selftest'ом (они не заходят в Windows-ветку)
  и всплывает только на машине владельца: так одна из сборок потеряла стиль
  сворачивания окна — `_fix_window_styles` упала на `wintypes`, а
  `except Exception` тихо превратил ошибку в WARN.
* **L49.** Автоопределение языка перевода дало язык, модели для которого у
  пользователя нет (be/uk/kk вместо ru — из-за одной буквы і/ў) → подмени
  исходный язык ближайшим языком ТОЙ ЖЕ письменности, если модель для него
  есть (`translator.fallback_language`) → иначе человек получает «Нет модели
  перевода be→en» на русском тексте и думает, что перевод сломан.

## 9. Как поддерживать эту инструкцию

* Столкнулся с новой ошибкой/неочевидностью, которой нет в разделе 8 → после
  решения допиши урок в конец нужного подраздела: одной строкой
  `* **Lnn.** если X → делай Y, иначе Z` (нумерацию продолжай).

  история граблей ценнее чистоты списка.
* Изменил процесс сборки/инструменты → обнови разделы 2 и 4 в том же коммите.
* Коммит с правкой инструкции пушится вместе с проектом
  (`gh-backup.sh push`), владелец видит актуальную версию на GitHub.
